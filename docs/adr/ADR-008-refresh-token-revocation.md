# ADR-008: Отзыв refresh-токенов — семейство, ротация, обнаружение повторного использования

- Статус: **Принято**
- Дата: 2026-11-06
- Этап: v0.3.1 «Безопасность + визуальная полировка»

## Контекст

В v0.3.0 (ADR-007) refresh-токен жил 30 дней и не имел механизма отзыва.
Это не теоретическая придирка, а три практические дыры:

1. **Кража refresh-токена.** Токен хранится в secure store, но утекает
   он не только оттуда: резервная копия устройства, скомпрометированное
   облако, лог старой версии клиента. Украденный refresh живёт месяц,
   и владелец ничего не может с этим сделать — «выйти» в v0.3.0 стирал
   токен только локально.
2. **Logout не инвалидировал сессию на сервере.** Пользователь на
   рыночном планшете выходит — а копия токена (если её снимали) gating
   продолжает работать.
3. **Смена роли не убивала чужие сессии.** `PATCH /users/me/role` менял
   роль в БД (guard перечитывает её из БД — привилегии не повышались),
   но старые refresh-токены других устройств продолжали обновляться.

## Решение

Паттерн **«Refresh Token Family + Rotation + Reuse Detection»** —
проверенная отраслевая практика (её описывает, например, Auth0
в «Refresh Token Rotation & Reuse Detection»):

- каждый вход (`/auth/verify`) открывает **семью** токенов с UUID
  `familyId`; несколько устройств = несколько независимых семей;
- при каждом `/auth/refresh` токен **ротируется**: старый `jti`
  помечается `used`, выдаётся новая пара с новым `jti`;
- повторное предъявление `used`-токена — признак того, что токен
  скопировали (у легитимного клиента он один и после ротации
  выбрасывается) → **вся семья отзывается**, легитимный клиент
  переходит на 401 и перелогинивается.

### 1. Хранение: Redis — источник решений, Postgres — журнал

```
session:family:<familyId>  → JSON { familyId, userId, status, currentJti, jtis[] }
session:jti:<jti>          → "<familyId>:<active|used|revoked>"
auth:access-blacklist:<jti> → "1" (TTL = остаток жизни access-токена)
```

- **Redis** — TTL ключей из коробки (равен TTL refresh-токена, при
  ротации продлевается) и общая память между репликами API. Решения об
  авторизации принимает только он.
- **Атомарность конкурентных refresh** — Lua-скрипт «проверить active →
  пометить used» (CAS): два одновременных запроса с одним токеном не
  пройдут оба; второй увидит `used` и попадёт в reuse detection.
- **Postgres `Session`** (миграция `20261106120000_session_revocation`) —
  аудит: `familyId`, `currentJti`, история `usedJtis`, `revokedAt`,
  `userAgent`, `ip`. Сбой записи аудита не убивает живую сессию
  (логируется), потому что Redis уже ротирован. Уникальные индексы по
  `familyId`/`currentJti`, каскадное удаление с пользователем.
- **Fail-closed во всех направлениях:** Redis недоступен → refresh
  отклоняется (401), access по блэклисту не проверяется → отклоняется,
  вход не выдаёт неотзываемые токены (503), logout честно отвечает 503,
  а не делает вид. В production отсутствие `REDIS_URL` роняет старт.
  Журналы помечают `degraded`.

### 2. Endpoints

```
POST /auth/refresh { refreshToken }
  → 200 { accessToken, refreshToken }   — НОВАЯ пара (ротация!)
  → 401 { code: "TOKEN_REUSE_DETECTED" } — семья отозвана
  → 401                                 — истёк/отозван/нет ключа

POST /auth/logout { refreshToken, accessToken? } → 204 (идемпотентен)
```

- Ротация возвращает **пару** токенов — клиент обязан заменить оба
  (`RefreshResponseDto` теперь пара; zod-схема строже).
- Logout отзывает семью целиком; access-токен (если передан) идёт в
  блэклист на остаток своих ≤15 минут. Мусорный/истёкший refresh в
  logout — тоже 204: «уже вышли».
- Rate limit `/auth/refresh` — 10 запросов/мин на IP.
- `PATCH /users/me/role` отзывает все семьи пользователя, кроме
  текущей (guard кладёт `familyId` access-токена в `request.auth`).
  Отзыв выполняется ДО смены роли: не смогли отозвать — роль не меняется.

### 3. Мобильный клиент

- `signOut` вызывает `POST /auth/logout` **до** локальной очистки
  (best-effort на обоих уровнях: сеть не должна запереть человека
  в аккаунте); затем чистит токены и outbox.
- 401 `TOKEN_REUSE_DETECTED` → принудительный выход на экран входа с
  мягким сообщением **«Сессия завершена. Войдите снова»** — без слова
  «кража»: пользователь ни в чём не виноват, паника в 4 утра не нужна.
- Токены v0.3.0 (без `jti`/`familyId`) вежливо отклоняются — чистый
  переход на новую версию, пользователь просто перелогинивается один раз.

## Альтернативы

- **Ревокация только по блэклисту refresh-jti без ротации** — не ловит
  кражу (вор и владелец живут на одном токене до конца месяца).
- **Короткий refresh-токен + «помнить устройство»** — усложняет UX
  рынка: продавец не должен логиниться каждую смену.
- **Сессии только в Postgres** — нет TTL из коробки, нужна чистка
  кроном, и каждый refresh — round-trip в БД. Redis уже в стеке
  (ADR-006/007).
- **Отзыв access-токенов списком сессий на каждый запрос** — дороже
  на каждом запросе; блэклист на остаток 15 минут — компромисс
  «мгновенный отзыв logout + естественное истечение».

## Последствия

- Кража refresh-токена обнаруживается при первой попытке его
  использования второй раз — вся семья умирает, вор и владелец
  перелогиниваются; владелец видит мягкое «Сессия завершена».
- Logout реально завершает сессию на сервере.
- Смена роли консистентна с сессиями других устройств.
- Redis становится обязательным в production (был настоятельным —
  ADR-006/007 — теперь старт-блокер).
- e2e-покрытие: ротация → повторное использование → мёртвая семья;
  logout → access и refresh невалидны; throttling; booking-флоу
  не регрессировал (25+ e2e против реальных Postgres+Redis в CI).
