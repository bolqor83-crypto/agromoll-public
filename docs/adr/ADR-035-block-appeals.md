# ADR-035: Блокировки 289-ФЗ — арбитражный разблок и апелляции

- Статус: **Принято**
- Дата: 2026-11-10
- Этап: v0.6.0 «Push, автодеплой, арбитраж, карта, админ» (подэтап E)
- Связанные: ADR-011 (учёт часов 289-ФЗ), ADR-015 (доставка попутчиками),
  ADR-033 (арбитраж споров), ADR-031 (push-уведомления)

## Контекст

Серия месяцев «60 ч+» закрывает пару водитель–продавец по 289-ФЗ (ADR-011):
`BlockedPair` создаётся автоматически, новые смены и доставки пары — 409.
Снятие блокировки в MVP — «вручную поддержкой»: процесс не описан, следов
разблока не остаётся, а ошибка в данных часов (например, смены закрывались
с ошибочной длительностью) оставляет пару заблокированной бессрочно.

Пользователю нужен честный механизм обжалования, а платформе — прозрачный
разблок с аудитом: кто, когда и почему снял блокировку. Естественный
исполнитель — уже существующая роль `arbitrator` (ADR-033): нейтральная
сторона рынка, не участник пары.

## Решение

### Блокировка становится историей, а не приговором

`BlockedPair` расширяется полями разблока: `unblockedAt` (когда снята),
`unblockedById` (кто — арбитр), `unblockReason` (обоснование). Уникальность
`@@unique([driverId, sellerId])` заменена частичным unique-индексом
`(driverId, sellerId) WHERE "unblockedAt" IS NULL`: **активна максимум одна
блокировка на пару**, но строка после разблока остаётся — аудит не
уничтожается. Повторная блокировка (серия закрылась снова после снятия)
«оживляет» существующую строку: `unblockedAt = NULL`, свежий `blockedAt` и
`reason` — тем самым `updateMany`-ревайв в `enforceSeriesLimit`, гонку двух
кронов ловит тот же частичный индекс (P2002 → тихо пропускаем, второй прогон
и так идемпотентен).

Все проверки «пара заблокирована?» теперь читают только АКТИВНЫЕ строки:
`findFirst({ where: { driverId, sellerId, unblockedAt: null } })` —
work-hours (смена, check, крон) и delivery-assign.

### Модель AppealCase

Апелляция — обжалование АКТИВНОЙ блокировки:

- `blockedPairId` — блокировка, на которую жалуются (FK);
- `driverId`/`sellerId` — пара, продублирована в кейсе: блокировка в
  будущем может быть снята, кейс — нет;
- `appellantId` — кто подал (водитель ИЛИ продавец пары — обе стороны
  страдают от блокировки, жалоба может прийти с любой);
- `reason` — суть: почему блокировка ошибочна;
- статус `open → under_review → unblocked | rejected`;
- `assignedToId`/`assignedAt` — арбитр, взявший в работу;
- `resolvedById`/`resolvedAt`/`notes` — решение и публичное обоснование.

**Один активный кейс на блокировку**: частичный unique-индекс
`(blockedPairId) WHERE status IN ('open', 'under_review')` — как «один
активный спор на объект» в ADR-033. После закрытия кейса (unblocked |
rejected) подать снова можно — например, после отклонения появились новые
данные. Гонку двух одновременных POST ловит индекс (P2002 → 409).

Переписки и доказательств в MVP нет: суть жалобы — текст `reason`, а
главное доказательство — сама история часов пары (месяцы, `totalMinutes`,
`monthCounted`), которую API отдаёт арбитру в деталях кейса. Если паре
нужны файлы — v0.7.0 вместе с S3 для доказательств споров.

### API

- `POST /appeals` — открыть (только сторона пары: driver/seller блокировки,
  не арбитр и не посторонний). Дубликат активного кейса → 409.
- `GET /appeals/mine` — мои кейсы: поданные мной ИЛИ по моей паре.
- `GET /appeals/queue` — очередь арбитра: активные, старые сверху.
- `GET /appeals/:id` — детали + месяцы часов пары (доказательство).
  Доступ: стороны пары и арбитры; посторонним — 404 (не раскрываем факт).
- `POST /appeals/:id/assign` — взять в работу (арбитр, из `open`).
- `POST /appeals/:id/resolve` — решение (арбитр, из `under_review`, только
  назначивший): `decision: unblock | reject`, `notes?`.

`unblock` — в ОДНОЙ транзакции: кейс закрывается (status `unblocked`) и
`BlockedPair` помечается снятой (`unblockedAt = now`, `unblockedById`,
`unblockReason = notes`). Пара может работать сразу: следующий
`POST /work-hours/sessions` пройдёт. `reject` — кейс закрывается
(`rejected`), блокировка остаётся; переподать можно с новыми данными.

### Заморозка предмета — не нужна

В отличие от споров по сделкам (ADR-033), предмет апелляции — блокировка —
сам меняется только решением арбитра в той же транзакции: стороны не могут
«испортить» её бизнес-операциями. Единственный конкурент — крон серий: он
ревайвит строку только если она уже активна... что и так блокировка.
Поэтому `assertNoActiveAppeal` для бизнес-переходов не требуется.

### Уведомления (ADR-031)

Новые типы: `appeal_opened` (контрагенту пары — второй стороне),
`appeal_assigned` и `appeal_resolved` (обеим сторонам пары). Решение
разблокирует работу пары — обе стороны должны узнать сразу, push-каналом.

### UI

- «Мои часы»: карточка заблокированной пары получает кнопку «Оспорить
  блокировку» (шторка с полем «что случилось», как OpenDisputeSheet) и
  бейдж статуса активной апелляции. Мягкий тон сохраняется: пауза по
  закону — не наказание, а возможность обжаловать — часть честности.
- «Арбитраж»: вкладка «Апелляции 289-ФЗ» рядом со спорами: очередь,
  кейс с историей месяцев пары, «взять в работу», разблок/отклонение
  с обоснованием.

## Последствия

- Миграция меняет уникальность `blocked_pairs`: существующие данные
  совместимы (у всех строк `unblockedAt IS NULL` → индекс строится без
  конфликтов).
- `findUnique(driverId_sellerId)` по блокировкам больше не существует:
  все чтения — `findFirst` с фильтром активности (work-hours, deliveries,
  e2e-тесты).
- Разблок арбитром не отменяет закон: если пара снова закроет серию
  месяцев, крон заблокирует её заново. Ревайв — не «вечный иммунитет».
- Репутация не страдает ни от блокировки, ни от апелляции: часы —
  юридическая страховка платформы, не наказание (ADR-011).
