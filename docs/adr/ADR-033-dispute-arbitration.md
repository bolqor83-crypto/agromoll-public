# ADR-033: Арбитраж споров

- Статус: **Принято**
- Дата: 2026-11-10
- Этап: v0.6.0 «Push, автодеплой, арбитраж, карта, админ» (подэтап C)
- Связанные: ADR-004 (модель брони и резерв), ADR-006 (идемпотентность),
  ADR-010 (долги и обоюдный спор), ADR-012 (confirm-delivery и спор по
  качеству), ADR-013 (публичный рейтинг), ADR-015 (доставка), ADR-031
  (push-уведомления)

## Контекст

Конфликты в сделках решаются сегодня двумя путями: спор по качеству
брони (major_issue, ADR-012) оставляет бронь в `disputed` навсегда,
а обоюдный спор по долгу (ADR-010) требует согласия обеих сторон.
Если стороны не договорились — тупик: продавец считает, что товар был
идеальным, покупатель — что половина разбита, и никто не может
закрыть сделку.

Нужен нейтральный арбитр: третья сторона рынка, которая рассматривает
спор по существу, выносит решение и приводит объект сделки
(бронь/долг/доставку) в финальное состояние.

## Решение

### Роль arbitrator — назначается, не выбирается

`UserRole` += `arbitrator`. Роль НЕ доступна через `PATCH /users/me/role`
(там только рыночные `MARKET_ROLES = buyer|seller|driver`): арбитром
назначают вручную/сидом. Самоназначение арбитром создавало бы прямой
конфликт интересов — «рассмотреть» собственный спор. Смена роли на
рыночную для арбитра технически возможна, но в UI арбитру не
предлагается (это осознанное решение администрации, не пользователя).

Стороны кейса фиксируются при открытии и не меняются:
`firstParty` — «покупательская» сторона (buyer/дебитор), `secondParty` —
«продавецкая» (seller/кредитор/доставщик). Термины «покупатель» и
«продавец» в решении — роль в спорной сделке, а не в системе.

### Модель данных

- `DisputeCase` — кейс: `type` (booking/delivery/debt) + `referenceId`,
  стороны, статус `open → under_review → resolved | dismissed`,
  решение, арбитр, обоснование.
- `DisputeMessage` — append-only переписка. `isInternal` — служебные
  заметки арбитра: **отдаются только роли arbitrator** (DTO-фильтр на
  стороне API, не «скрыть в UI» — данные не должны доехать до клиента).
- `DisputeEvidence` — доказательства: base64 ≤ 2 МБ, хранение в БД
  (MVP; S3 — v0.7.0), в DTO отдаются только метаданные.

**Один активный спор на объект**: частичный unique-индекс
`(type, referenceId) WHERE status IN ('open', 'under_review')`.
Повторное открытие → 409; гонку двух одновременных POST ловит именно
индекс (P2002 → 409), сервисная проверка — быст путь. После закрытия
кейса спор по объекту можно открыть снова.

### Заморозка объекта

Пока спор активен, бизнес-переходы объекта возвращают 409:
- бронь: counter-offer / accept-counter / confirm / cancel /
  confirm-delivery + кроны TTL и авто-подтверждения (молча skip);
- долг: settle / dispute / resolve / reminder;
- доставка: assign / start / deliver / cancel + TTL-крон.

Заморозка — защита предмета спора: стороны выясняют отношения в
арбитраже, а не меняют бронь «под ногами» у арбитра. Проверка
`DisputesService.assertNoActiveDispute(type, id, tx?)` вызывается
внутри транзакций переходов (тот же снимок БД). Окно гонки «спор
открылся в момент перехода» — миллисекунды, для MVP принято осознанно.

### Решение и судьба объекта

`POST /disputes/:id/resolve` (только арбитр, только из `under_review` —
сначала взял в работу): всё в ОДНОЙ транзакции:

- **Бронь** (`bookingOutcome`): `cancel` — отменена, резерв возвращён
  листингу тем же атомарным SQL, что и обычная отмена (ADR-004);
  `complete` / `complete_minor` — завершена как принятая (ok /
  minor_issue), событие `delivery_confirmed` с `byArbitration: true`.
- **Долг** (`debtOutcome`): `cancel` — отменён; `restore_active` —
  возвращён в активные (спор снят); `settle_adjusted` — погашен со
  сниженной суммой (`adjustedAmount` ≤ исходной, «скидка», не доначисление).
  Спорный статус долга (ADR-010) закрывается событием `resolve_confirmed`
  — оно нейтрализует минус спорного события в рейтинге дебитора.
- **Доставка** (`deliveryOutcome`): `cancel` или `none` — оставить
  сторонам (у доставки нет «приёмки», судьба репутации решается
  штрафами, маршрутные последствия — их дело).

`no_fault` и `dismiss` объект не трогают: разморозка automatic —
активного спора больше нет, стороны продолжают сами.

### Репутация: штрафы из кейсов, журнал — источник правды

Вес решений (ENV, дефолты спецификации):

| Решение       | firstParty (покупатель) | secondParty (продавец) |
|---------------|-------------------------|------------------------|
| favor_buyer   | —                       | **−1.0**               |
| favor_seller  | **−1.0**                | —                      |
| compromise    | **−0.5**                | **−0.5**               |
| no_fault      | —                       | —                      |

Штраф учитывается в `ReputationService.computeFromEvents` из закрытых
кейсов напрямую (кейс = одна единица данных в знаменателе, как другие
события спора) — пересчёт идемпотентен, доехавший «позже» триггер ничего
не ломает. Человекочитаемый аудит — `ReputationEvent(penalty_applied)`.
Триггер `safeOnDisputeResolved` вызывается ПОСЛЕ транзакции решения и
никогда не бросает: сбой пересчёта не откатывает решение арбитра
(паттерн ADR-013).

### API

- `POST /disputes` — открыть (только сторона; идемпотентно);
- `GET /disputes` — мои кейсы; `GET /disputes/queue` — очередь арбитра;
- `GET /disputes/:id` — детали (внутренние заметки — только арбитру);
- `POST /disputes/:id/messages` / `:id/evidence` — активный кейс;
- `POST /disputes/:id/assign` — взять в работу (арбитр);
- `POST /disputes/:id/resolve` — решение (арбитр).

Постороннему кейс не виден: 404, а не 403 — не раскрываем сам факт
спора между другими участниками. Уведомления `dispute_*` идут по
каналам ADR-031 (in-app + push), deep link — в «Споры» (арбитру — в
очередь).

## Альтернативы

- **Расширить обоюдный спор долга (ADR-010) на все объекты** —
  отвергнуто: тупик при несогласии сторон остаётся, нужен арбитр.
- **Куратор рынка (один админ)** — отвергнуто: роль и очередь —
  минимальный каркас для нескольких арбитров, один «админ всем»
  не масштабируется и единственная точка отказа.
- **Хранить переписку в чат-сервисе** — отвергнуто для MVP: append-only
  таблица проще, аудитируемее и не тянет инфраструктуру.

## Последствия

- Кейсы арбитража — третий append-only журнал домена (после
  BookingEvent/DebtEvent): история споров восстанавливается целиком.
- Мобильный UI: «Споры» (стороны) и «Арбитраж» (очередь арбитра)
  — root-экраны с ленивыми чанками (ADR-023), эскалация — из карточек
  броней и долгов.
- Доказательства в БД ограничены 2 МБ — для рынка этого достаточно
  (фото разбитых ящиков); S3 + превью — v0.7.0.
- Апелляции на решения и разблокировки 289-ФЗ — подэтап E (ADR-035):
  AppealCase переиспользует роль арбитра и этот же каркас.
