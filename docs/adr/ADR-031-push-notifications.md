# ADR-031: Push-уведомления

- Статус: **Принято**
- Дата: 2026-11-09
- Этап: v0.6.0 «Push, автодеплой, арбитраж, карта, админ» (подэтап A)
- Связанные: ADR-010 (долги и первые in-app уведомления), ADR-012
  (confirm-delivery), ADR-013 (репутация), ADR-015 (доставка), ADR-023
  (code splitting), ADR-027 (анимации)

## Контекст

Доставка и брони работают, но «немая» логистика: покупатель не знает,
что водитель взял заказ; продавец не знает, что бронь подтверждена;
должник узнаёт о напоминании только открыв приложение. In-app уведомления
(v0.4.0) требуют захода в приложение — их читают постфактум.

Требуется push: доставка статусов на устройство без открытия приложения,
на native (iOS/Android) и web (браузерный web-экспорт — демо-платформа).

## Решение

### Транспорт: FCM HTTP v1 (native) + Web Push/VAPID (web)

- **Native**: expo-notifications на клиенте получает Expo Push Token
  (под капотом FCM/APNs). Сервер шлёт через **FCM HTTP v1** с сервисным
  аккаунтом (`FCM_SERVICE_ACCOUNT_JSON`, JSON или base64): OAuth2-токен
  получается JWT RS256 через встроенный `node:crypto` — **без
  firebase-admin SDK** (одна зависимость меньше, один ключ в ENV).
  Legacy HTTP API (использовался в v0.4.0 как заготовка) выключен
  Google — v1 единственный живой путь.
- **Web**: Web Push API — service worker (`public/sw.js`, NO-OP для
  fetch, только push/notificationclick) + PushManager.subscribe c
  публичным VAPID-ключом сервера. Отправка — библиотека **web-push**
  (VAPID JWT + шифрование aes128gcm по RFC 8291): криптографию руками
  не пишем, проверенная реализация надёжнее. Публичный ключ клиент
  берёт с `GET /notifications/vapid-public` — ротация ключа без
  пересборки бандла.

Платформенное разделение клиента — `register-push.ts` (web) /
`register-push.native.ts` (native) с **одинаковым API** (паттерн
ADR-023): потребитель (NotificationCenter) платформы не знает,
expo-notifications не попадает в web-бандл.

### Модель данных

- `DeviceToken` — FCM-токены устройств: уникален по `token`, upsert при
  повторной регистрации (перелогин перепривязывает токен пользователю).
  Один пользователь — много устройств.
- `WebPushSubscription` — веб-подписки: уникальны по `endpoint`,
  хранят ключи шифрования `p256dh`/`auth` (RFC 8291).
- `NotificationLog` — журнал доставок для аудита: канал, статус
  (sent/failed/delivered), текст ошибки. Пользователь видит свои записи
  (`GET /notifications/log`) — разбор «не пришло».
- `User.fcmToken` **удалён**: колонка была мёртвой с v0.4.0 (ни один
  код не записывал её), правильная модель — DeviceToken.

### Каналы и гарантии

`NotificationsService.send()` (существующий контракт сохранён) пишет:

1. **In-app строку** (таблица notifications) — единственный
   гарантированный канал: работает без Firebase, читается поллингом.
2. **Push на все устройства** пользователя: FCM-токены + веб-подписки,
   параллельно. Транспорт выбирается по адресу (токен → FCM,
   подписка → web-push), а не по конфигурации.

`sendToRole(role, …)` — broadcast роли (например, водителям о новых
заказах в коридоре): итерация по пользователям роли через тот же send.

**Push — best-effort**: сервис не бросает исключений, сбой доставки не
откатывает бизнес-операцию (как в ADR-010/012/013 — уведомление
вспомогательный канал). Все уведомления отправляются ПОСЛЕ фиксации
бизнес-транзакции.

### Очередь: in-memory с retry

Доставка идёт через очередь в памяти процесса: при сбое — пауза
`1000·2^(n−1)` мс и повтор, максимум **3 попытки**, итог каждой попытки —
в NotificationLog (последняя определяет статус).

Почему in-memory, а не внешний брокер (Redis Streams / BullMQ):

- уведомление — не платёж, потеря одного push не стоит инфраструктуры;
- in-app строка уже гарантирует доставку содержимого;
- очередь нужна только для сглаживания сетевых люков провайдера.

Компромисс: рестарт сервера теряет недоставленные push — принимается.

### События (v0.6.0-A)

- **Бронь**: counter_offered → покупателю; confirmed (прямое и через
  accept-counter) → покупателю/продавцу; cancelled → другой стороне.
- **Доставка**: assigned/started/delivered → покупателю; cancelled →
  другой стороне (если была взята).
- **Долг**: reminder → дебитору (rate limit 24 ч — уже был, ADR-010).
- **Репутация**: score упал ниже 3.0 → мягкое «обратите внимание на
  качество». Только при пересечении порога сверху вниз — дальнейшие
  падения молчат (анти-спам).
- **Dispute (заложено)**: перечисление `NotificationType` расширяемо,
  hook подключит подэтап C (арбитраж) — события споров пока не
  отправляются.

### Клиент: push — сигнал, не источник данных

- Тап по уведомлению/тосту → **deep link** к объекту (`data.bookingId`/
  `deliveryId`/`debtId` → маршрут expo-router), экран перечитывает
  данные с сервера. Push никогда не является источником истины.
- **NotificationCenter** (монтируется после входа): регистрирует канал,
  поллит `GET /notifications/me` каждые 30 с, новые уведомления →
  тост (Toast из дизайн-системы: Inter, скругление 16, тени 2 слоя,
  SlideInDown/reduced-motion) + version-bump в notification-store —
  экраны-цели (брони, доставка, долги, входящие, радар) перечитывают
  данные (механизм как у outbox-версий).
- Поллинг — осознанный компромисс: web-экспорт живёт без VAPID-ключей
  (dev/CI), in-app канал обязан работать везде; push лишь ускоряет.
- **Отказ в разрешении** — не блокирует: мягкий баннер «Включите
  уведомления» с кнопкой «Настроить»/«Позже», закрывается навсегда
  (флаг в AsyncStorage/localStorage, как онбординг ADR-029).
- Service worker (web): push → showNotification; notificationclick →
  фокус вкладки + postMessage → deep link (или openWindow с hash).

### API

- `POST /notifications/register` — регистрация канала: `{platform:
ios|android, token}` или `{platform: web, endpoint, p256dh, auth}`.
  Идемпотентно (upsert).
- `DELETE /notifications/unregister` — при logout (best-effort).
- `GET /notifications/log` — журнал своих доставок.
- `GET /notifications/vapid-public` — публичный ключ (null — не
  настроен).

Отправки «извне» нет: уведомления порождаются только бизнес-событиями
внутри сервера (как в v0.4.0).

## Тестирование без Firebase

В CI нет устройств и ключей: транспорты без ENV — Noop (доставка
«успешна» вхолостую), e2e проверяет контракты — регистрацию токенов
(upsert/дедупликация/перепривязку), записи NotificationLog по
бизнес-событиям, журнал, unregister. Реальная доставка проверяется
вручную при наличии ключей (ENV в .env, не в репозитории).

## Последствия

- Покупатель видит «водитель взял заказ» не открывая приложение;
  продавец — «бронь подтверждена»; должник — напоминание.
- Добавлены зависимости: web-push (api), expo-notifications (mobile,
  только native-бандл).
- ENV: FCM_SERVICE_ACCOUNT_JSON, VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY,
  VAPID_SUBJECT, PUSH_RETRY_BASE_MS (все опциональны — без них каналы
  тихо выключены).
- Миграция 20261109000000_push_notifications: три таблицы, расширение
  NotificationType, удаление мёртвого users.fcmToken.
