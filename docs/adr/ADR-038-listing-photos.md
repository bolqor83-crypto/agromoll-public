# ADR-038: Реальные фото товаров

- Статус: принято (v0.7.0-D)
- Дата: 2026-11-07
- Связанные: ADR-036 (S3-хранилище доказательств — источник механики),
  ADR-028 (карточки и «фото» 4:3 в деталях — задел под этот этап),
  ADR-026 (честный демо-режим: без фото — иконка, без вранья)

## Контекст

До v0.7.0 карточка лота обходилась иконкой-заглушки по категории:
«Помидоры розовые» и «Перец болгарский» выглядели одинаково (листок
Ionicons). Покупатель в ленте выбирал по названию и цене — вслепую.
На оптовом рынке фото решают: сорт, калибр, тара, состояние партии.
Экран деталей с v0.6.2-B уже готовил место: фрейм 4:3 с комментарием
«когда появятся реальные фото, текст поверх будет читаться».

Механика загрузки файлов уже существовала для доказательств споров
(ADR-036): presigned PUT → confirm с objectKey (сверка HEAD) либо
fallback data:-URL ≤ 500 КБ. Переизобретать нечего — этот ADR
переиспользует контракт дословно и фиксирует отличия.

## Решение

**ListingPhoto — до 5 фото на лот, тем же механизмом, что DisputeEvidence.**

### Модель

- `id, listingId (FK, cascade), position Int, fileName, mimeType,
  sizeBytes, fileUrl @db.Text, createdAt` + `@@unique([listingId, position])`.
- `fileUrl` — те же две формы: `s3://listings/<listingId>/<uuid>.<ext>`
  или `data:<mime>;base64…` (fallback). Один бакет на все файлы
  (`agromoll-evidence`): изоляция — префиксами ключей, а не бакетами.
- **position 0..4, обложка = 0**: карточки ленты/витрины запрашивают
  только первое фото (`take: 1, select: { fileUrl }`) — тащить пятёрку
  ссылок в каждый элемент ленты незачем. Уникальность (listingId,
  position) страхует от гонки параллельных attach (P2002 → 409).
- Удаление пересобирает позиции: после удаления обложки обложкой
  становится следующее фото, дыр нет — обложка всегда ищется по 0.

### Эндпоинты (владелец лота — проверка в сервисе, не ролями)

- `POST /listings/:id/photos/upload-url` `{mimeType, sizeBytes}` —
  503, если хранилище не настроено (клиент уходит в fallback);
- `POST /listings/:id/photos` — `@Idempotent('listing_photo')`,
  дискриминатор storage s3/data (как DisputeEvidenceSchema);
- `DELETE /listings/:id/photos/:photoId` — удалить, позиции пересобрать.
- `GET /listings` и `GET /listings/mine` дополняются `coverUrl`
  (presigned GET / data:-URL / null), `GET /listings/:id` — `photos[]`
  с ссылками. Оба поля опциональны в zod-схеме ответа: старый сервер
  не ломает клиент (как sellerRating в ADR-013).

Разрешённые типы — только изображения (jpeg/png/webp): **без pdf**.
Это витрина, а не арбитраж: pdf-накладная на карточке товара —
не пользовательская история. Лимит 10 МБ (presigned) / 500 КБ
(fallback) — как у доказательств.

### Мобильные экраны

- **Создание** (CreateListingModal): плитки 64×64 с превью (uri сжатой
  копии — манипулятор его уже вернул) + пунктирная «+»: мультивыбор
  галереи (`selectionLimit` = остаток слотов), до 5. Фото грузятся
  ПОСЛЕ создания лота, по очереди: ошибка фото не роняет лот —
  «Лот создан, но не всё фото загрузились» + счётчик. Некритичные
  данные не блокируют критичные (противоположность доказательствам,
  где loss недопустим).
- **Карточка** (ListingCard): обложка 56×56 в морф-якорe; onError →
  иконка категории (деградация, не пустой квадрат). Без фото —
  иконка, как раньше.
- **Детали** (ListingDetailScreen): карусель FlatList pagingEnabled
  + точки-индикаторы; тап — полноэкранная галерея (Modal, свайп,
  счётчик «2 / 5», крестик). Без фото — прежняя иконка (демо-данные).
- Офлайн-очередь не используется: файл в S3 не повторить идемпотентно,
  прямой POST с `X-Idempotency-Key` — паттерн доказательств (ADR-036).

## Альтернативы

- **Base64 прямо в Listing (поле photosJson)** — отвергнуто: БД пухнет
  мегабайтами на лот, лента тяжелеет кратно. Fallback ≤ 500 КБ остаётся
  крайним случаем, а не основным путём.
- **Отдельный бакет под фото** — отвергнут: изоляция достигается
  префиксом ключа (`keyBelongsToListing`), второй бакет — вторая
  точка конфигурации без выгоды.
- **Сортировка перетаскиванием (drag-and-drop позиций)** — отложено:
  порядок = порядок загрузки, первые фото грузят первыми (они и есть
  главные). Перетаскивание — отдельная UX-задача, если продавцы
  попросят.
- **Webhook-обработка изображений (миниатюры, водяные знаки)** —
  отложено: клиент сжимает до 1200 px/JPEG 80 до загрузки (photo.ts),
  карточке 56×56 этого достаточно с запасом.

## Тестирование

- Unit (API): upload-url владелец/403/503; attach s3 happy/чужой
  ключ/файла нет/размер не совпал; data happy/MIME-расхождение; лимит
  5 → 409; delete пересобирает позиции/404/403; coverUrl в findMany
  (presigned и data:), photos в findOne. StorageService: ключ
  listings/<id>/…, keyBelongsToListing, изоляция от disputes/.
- Unit (mobile): photo-upload — S3-путь, 503 → fallback, PUT упал →
  fallback, >500 КБ → too_large_for_fallback, confirm упал → без
  дублирования, network. Validation: схемы s3/data/лимиты/опциональность
  coverUrl в ответе.
- E2E (CI, LocalStack): полный S3-цикл с байтами, обложка в ленте
  и витрине, fallback ≤/› 500 КБ, шестое фото 409, доступ 403/404,
  удаление с пересборкой позиций.

## Последствия

- Миграция: таблица `listing_photos` + `listing_photo` в
  OutboxOperationType (идемпотентность attach).
- StorageModule импортируется ListingsModule — S3-конфиг один на все
  файлы (S3_* в env, см. .env.example).
- Fallback-режим (без S3) честно тяжелеет: data:-обложки в ленте.
  Это осознанный trade-off dev/демо; прод-путь — managed-бакет
  (DEPLOY.md, вариант a-1).
- Демо-данные (без API) остаются без фото — иконки категорий,
  как и раньше (ADR-026: не рисуем выдуманные фото).
