# ADR-012: Приёмка и закрытие брони — confirm-delivery, терминальный completed, авто-подтверждение

- Статус: **Принято**
- Дата: 2026-11-07
- Этап: v0.4.0 «Долги · Учёт часов 289-ФЗ · Приёмка» (подэтап C)

## Контекст

До v0.4.0 жизненный цикл брони обрывался на `confirmed`: продавец
подтвердил бронь, товар ушёл — и всё. Бронь «повисала» навсегда:
непонятно, получил ли покупатель товар, доволен ли качеством, завершена
ли сделка. Из такой незавершённости невозможно считать ни репутацию,
ни надёжность, ни даже просто «активные» сделки.

Подэтап C закрывает цикл: покупатель подтверждает приёмку — бронь
завершается. Фиксируется фактически полученное количество и оценка
качества — это первые реальные данные для репутации v0.5.0.

## Решение

### Переходы: confirmed → completed | disputed

```
confirmed ──(buyer: confirm-delivery, ok/minor)──► completed
confirmed ──(buyer: confirm-delivery, major)─────► disputed
confirmed ──(cron: 24 ч без приёмки)─────────────► completed (system_auto_confirmed)
```

- **Только покупатель** (403 остальным): приёмка — подтверждение
  получения, получить может только получатель.
- **Только из confirmed** (409 из прочих): подтвердить приёмку
  неподтверждённой брони бессмысленно.
- **completed терминальный**: отмена завершённой сделки — это
  «расзавершение» истории; спор уже не вспять, журнал append-only.
  Отмена по-прежнему доступна только из requested/counter_offered.

### QualityFlag: ok / minor_issue / major_issue

- **ok** — всё в порядке → completed.
- **minor_issue** — мелкие проблемы: бронь ВСЁ РАВНО завершается
  (недостача зафиксирована в receivedQuantity и журнале), сделка
  состоялась. Недостача (receivedQuantity < confirmedQuantity)
  автоматически ставит minor_issue, даже если покупатель забыл
  переключить оценку: данные о качестве важнее мнения о нажатой кнопке.
- **major_issue** — серьёзная проблема → **disputed**, не completed и
  не отмена. Почему спор, а не отмена: отмена возвращает резерв и
  делает вид, что сделки не было — но товар физически получен (пусть
  и плохой). Спор честно фиксирует: сделка была, есть претензия.
  Арбитраж — v0.5.0; в v0.4.0 спор — запись + уведомление продавцу
  (стороны решают на рынке, платформа не судья).

Покупатель может явно поставить major_issue даже при полной недостаче:
серьёзность — его оценка, сервер только поднимает планку снизу (ok →
minor при недостаче), но не занижает сверху.

### Авто-подтверждение через 24 часа

`BookingAutoConfirmCron` ежечасно завершает брони в `confirmed` старше
`BOOKING_AUTO_CONFIRM_HOURS` (24 по умолчанию): completed, qualityFlag=ok,
`system_auto_confirmed` (actorId NULL). Мотивация: продавец не должен
нести репутационные издержки из-за забывчивости покупателя; без
авто-подтверждения «подтверждено сделок» продавца зависело бы от
дисциплины чужих людей.

Окно отсчитывается от `confirmedAt` — подтверждения брони продавцом.
Спецификация называла якорем «отметку доставки водителем (delivered_at),
иначе TTL», но потока доставок в v0.4.0 нет (radar/deliveries — заглушки
v0.1.0): delivered_at появится в v0.5.0, и крон перейчется на него —
поле уже в схеме, логика якоря локализована в `autoConfirmStale`.
Отклонение зафиксировано здесь намеренно.

### Триггеры при confirm-delivery

1. **Репутационные счётчики**: продавцу `totalConfirmations++` при
   completed, `totalDisputes++` при disputed. Счётчики — быстрый view
   («Подтверждено сделок: 42» на витрине); источник правды для рейтинга
   v0.5.0 — события, счётчики пересчитываются из журнала при расхождении.
2. **Уведомление продавцу** (in-app + push при наличии ключа):
   «Приёмка подтверждена» или «Спор по приёмке». NotificationsService —
   тот же, что у долгов (ADR-010): best-effort, сбой не откатывает сделку.
3. **Закрытие рабочей смены**: если покупатель — водитель с открытой
   сменой у продавца этого лота (сценарий самовывоза), смена закрывается
   через `WorkHoursService.endSession` (ADR-011): часы пары должны
   попасть в месяц. Сбой закрытия не откатывает приёмку — лог + ручное
   закрытие.

### Идемпотентность и офлайн

`confirm_delivery` помечен `@Idempotent` (в enum OutboxOperationType
заложен ещё в v0.3.0): двойная отправка с одним X-Idempotency-Key
не создаёт дубль события. Мобильный клиент отправляет приёмку через
outbox — подтверждение работает и без сети (оптимистичный статус
completed/disputed по выбранной оценке качества).

## Альтернативы

- **Автоматически завершать бронь при confirm продавца.**
  Отвергнуто: подтверждение брони — обещание отгрузить, приёмка — факт
  получения. Разные события, разные люди, разное время.
- **major_issue → отмена с возвратом резерва.**
  Отвергнуто (выше): сделка физически состоялась, «расотменить»
  историю нельзя — журнал append-only.
- **Без авто-подтверждения, ждать покупателя вечно.**
  Отвергнуто: подвешенные брони ломают статистику и вредят продавцу.
- **Слайдер количества с дробными значениями.**
  Отвергнуто: единицы рынка (кг/ящик/шт) — целые, zod требует int.

## Последствия

- BookingEvent пополнился тремя действиями — репутация v0.5.0 считает
  «успешность сделок» прямо из журнала, без новых сущностей.
- `confirmedAt` пишется и в confirm, и в acceptCounter — якорь один
  для обоих путей подтверждения брони.
- v0.5.0: арбитраж споров (медиация платформы), пересчёт счётчиков
  из журнала, delivered_at как якорь авто-подтверждения.
