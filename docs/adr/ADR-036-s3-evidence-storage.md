# ADR-036: S3-хранилище для доказательств споров

- Статус: принято (v0.7.0-B)
- Дата: 2026-11-07
- Связанные: ADR-033 (арбитраж споров), ADR-031 (push: тот же принцип
  «деградация, а не падение»), ADR-038 (фото товаров — тот же механизм)

## Контекст

Доказательства споров (фото разбитых ящиков, сканы накладных) с v0.6.0
хранились как base64 в колонке `dispute_evidence.dataBase64` (лимит 2 МБ,
zod на входе). Решение было осознанным MVP (ADR-033), но не масштабируется:

- БД пухнет: 10 споров × 5 фото × 2 МБ — уже 100 МБ в Postgres, бэкапы
  и репликация дорожают, shared_buffers вытесняются;
- двойной трафик: файл идёт клиент → API → БД, затем БД → API → арбитр;
- логи/снапшоты БД таскают мегабайты user-контента.

## Решение

**S3-совместимое хранилище + presigned URL, в БД — только ссылки.**

### Выбор провайдера: не выбираем — S3-API как стандарт

Код написан против S3-протокола (`@aws-sdk/client-s3` + `s3-request-presigner`),
провайдер меняется конфигом `S3_*`, без правок кода:

| Провайдер | Когда уместен | Примечания |
|---|---|---|
| **LocalStack 4.14.0** | dev/CI, self-hosted | последний свободный community-релиз (см. ниже); бакет создаётся сам |
| AWS S3 | дефолтный выбор прода | виртуальные хосты (`forcePathStyle=false`) |
| Cloudflare R2 | трафик-heavy | zero egress — отдача фото арбитрам бесплатна |
| Yandex Object Storage | прод в РФ | низкая латентность для ростовского рынка |

**Почему не MinIO (был первым кандидатом):** MinIO перестал
публиковать бесплатные образы на Docker Hub (октябрь 2025) и заархивировал
community-репозиторий (февраль 2026); анонимный pull `minio/minio` и
`quay.io/minio/minio` больше не работает (свидетели: Milvus issue #53430
и др.).

**Почему LocalStack именно 4.14.0:** с релиза 2026.03.0 LocalStack
объединил community/pro образы и требует `LOCALSTACK_AUTH_TOKEN` даже
для S3 — аккаунт и лицензия на каждый CI-запуск нам не нужны. 4.14.0
(26.02.2026) — последний свободный community-релиз; пин — осознанный
trade-off (без обновлений образа) с задокументированным пересмотром.
На прод-выбор это не влияет: AWS/R2/Yandex никуда не делись, а код
между провайдерами не меняется — тестовый двойник заменяем отдельно.

Формат `fileUrl` в БД — `s3://<objectKey>` (ключ без имени бакета:
бакет в конфиге, переименование не ломает строки) или
`data:<mime>;base64,…` (fallback, см. ниже). Одна колонка, две формы —
различаются по схеме, `s3KeyFromFileUrl()` возвращает null для data:-URL.

### Почему presigned URL, а не загрузка через API

Presigned PUT — это подписанная (SigV4) ссылка, по которой клиент кладёт
файл **напрямую в хранилище**:

- API не перекачивает мегабайты и не держит HTTP-соединение на время
  загрузки (мобильный интернет на рынке — связь рвётся);
- лимит тела API остаётся 4 МБ для JSON — фото до 10 МБ идут мимо;
- подпись — локальная криптография (без сети), генерация дешёвая;
- ссылка короткоживущая (10 мин) и одноразовая по смыслу: утечка
  логов не даёт перманентного доступа.

Обратная сторона: web-клиенту нужен CORS на бакете (PUT с другого
origin). LocalStack и большинство self-hosted CORS не валидируют;
для облачного прода — один ручной шаг (см. «Ручные шаги» ниже).
Native CORS не касается.

### Поток (три шага)

1. `POST /disputes/:id/evidence/upload-url` `{mimeType, sizeBytes}` →
   проверка доступа (участник/арбитр) + лимитов (10 МБ, allowlist MIME:
   jpeg/png/webp/pdf) → `{objectKey, uploadUrl, expiresIn}`;
   ключ = `disputes/<disputeId>/<uuid>.<ext>`.
2. Клиент делает `PUT uploadUrl` с байтами файла (S3 напрямую).
3. `POST /disputes/:id/evidence` `{storage:'s3', objectKey, …}` —
   сервер проверяет: ключ выдан для ЭТОГО спора (префикс — доказательство
   спора A нельзя прицепить к спору B), объект существует (HEAD), размер
   и MIME совпали с заявленными. Только после этого строка в БД.

`GET /disputes/:id/evidence` — список с presigned GET (1 час): ссылки
живут недолго, «утёкший» скриншот перестаёт работать. Доступ — тот же,
что к кейсу (участники + арбитр), посторонним 404.

### Fallback: data:-URL ≤ 500 КБ

Хранилище не настроено / лежит → `upload-url` отвечает 503, и клиент
повторяет подтверждение формой `{storage:'data', dataUrl}`. Мобильный
клиент делает это автоматически (сжатое фото 1200px/q80 обычно < 500 КБ),
пользователь ничего не замечает. Логика — как с push (ADR-031):
вспомогательная инфраструктура не должна валить основной сценарий,
критические доказательства не теряются.

Лимит 500 КБ (в 4 раза меньше старого 2 МБ) удерживает БД от распухания:
fallback — исключение, а не норма. Fallback после УСПЕШНОГО PUT не
включается (файл уже в хранилище — повтор создал бы дубль; честная
ошибка `upload_failed` и повтор пользователем).

### Миграция данных

Существующие base64-строки конвертируются в data:-URL той же миграцией,
что меняет колонку: файл в S3 для них не существует, а терять
доказательства закрытых кейсов нельзя (журнал — источник правды,
ADR-033). Прода-БД нет — конвертация релевантна только для dev/CI.

## Ручные шаги для прода (документируем, не «костылим»)

1. Завести бакет у провайдера (или дать права на CreateBucket —
   StorageService создаст сам и залогирует).
2. Для web-клиента: CORS-правило бакета `PUT` (и `GET` не нужен —
   presigned GET браузер тоже грузит CORS-ом: разрешить оба метода,
   origin = домен web-приложения).
3. Задать `S3_ENDPOINT/S3_BUCKET/S3_ACCESS_KEY/S3_SECRET_KEY` на PaaS,
   где живёт API (не в Vercel web-проекта — см. отчёт v0.7.0-A).

## Тестирование

- **Unit** (моки): конфигурация/деградация StorageService, генерация
  ключей, presign-ответы, access-проверки, чужой objectKey → 400,
  размер/MIME не совпали → 400, fallback-лимиты, мобильный поток
  (S3-путь, 503 → fallback, >500 КБ → честная ошибка, без дублей).
- **E2E против реального S3 (LocalStack, CI service-контейнер):**
  upload-url → PUT байт → confirm → GET списка → GET по ссылке отдаёт
  ровно те же байты; fallback data:-URL; посторонний — 404.
- Регрессии: все прежние сценарии споров (заморозка, решения, репутация)
  не изменены — подтверждается существующими e2e.

## Последствия

- `DisputeEvidence.dataBase64` → `fileUrl` (+ миграция с конвертацией);
- новые эндпоинты `/disputes/:id/evidence/upload-url` и
  `GET /disputes/:id/evidence`;
- `StorageModule` переиспользуется фото товаров (ADR-038);
- docker-compose и CI получают S3-сервис (LocalStack; MinIO ушёл с
  Docker Hub — см. «Выбор провайдера»);
- prod-инфраструктура: один ручной шаг (бакет + CORS), задокументирован
  здесь и в DEPLOY.md.
