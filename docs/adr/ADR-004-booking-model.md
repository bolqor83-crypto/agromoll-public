# ADR-004: Модель бронирования

- Статус: **Принято**
- Дата: 2026-11-05
- Этап: v0.2.0 «Бронирование»

## Контекст

Главный сценарий рынка в 4–14 утра: покупатель (ларёк) видит лот в ленте и
просит зарезервировать количество до приезда. Продавец может подтвердить
запрос как есть либо предложить корректировку (другое количество, другое
время выкупа). Бронь живёт недолго: товар скоропортящийся, «висящие»
запросы держат остатки и мешают другим покупателям.

Нужны: модель данных, строгая машина состояний, защита остатков от
перепродажи и журнал для будущей репутации.

## Решение

### 1. Модель данных

```
User 1───n Listing 1───n Booking 1───n BookingEvent
                │            │
                └── sellerId └── buyerId → User
```

- **Listing** — лот продавца: `quantityAvailable` (всего) и
  `quantityReserved` (держат брони). Свободно к бронированию =
  `quantityAvailable − quantityReserved`. Индексы по `sellerId`, `status`,
  `category` — под ленту и витрину.
- **Booking** — бронь покупателя: `requestedQuantity`, `confirmedQuantity`,
  `status`, `expiresAt` (TTL). Индексы по `buyerId`, `listingId`, `status`.
- **BookingEvent** — append-only журнал: строки только добавляются,
  ничего не обновляется и не удаляется. Репутация участника в будущем
  считается именно из журнала, поэтому он обязан быть полным: каждое
  изменение статуса брони = ровно одна запись с `actorId` и `payload`.

**Отступление от ТЗ (согласовано в отчёте):** `BookingEvent.actorId` —
nullable. Истечение TTL по кроне — системное действие без человека-актёра;
заводить фиктивного «пользователя system» ради NOT NULL означало бы
шум в будущей репутационной статистике.

### 2. Статусы: почему именно requested / counter_offered / confirmed / cancelled / expired

```
requested ──(seller)──► confirmed
   │  │
   │  └──(seller)──► counter_offered ──(buyer)──► confirmed
   └─(любая сторона)─► cancelled ◄─(любая сторона)─ counter_offered

requested / counter_offered ──(cron, истёк TTL)──► expired
```

- **counter_offered — отдельный статус, а не флаг.** Корректировка меняет
  суть сделки (кто должен решить — покупатель), поэтому «чей ход» должен
  быть виден в списке броней без разбора JSON-журнала. В UI это «Уточняется»
  (янтарная пилюля).
- **Подтверждённую бронь нельзя отменить в v0.2.0** (нет перехода
  confirmed → cancelled): у подтверждённой брони другое экономическое
  содержание — продавец уже отложил товар. Отдельный процесс «не выкупил»
  с влиянием на репутацию появится вместе с выкупом и долгами (v0.3+).
- **expired отдельно от cancelled.** Причина окончания важна для репутации:
  «покупатель не ответил» и «кто-то осознанно отменил» — разные сигналы.

### 3. quantityReserved на листинге, а не сумма по броням

Доступный остаток читается одним чтением листинга (без агрегации по
живым броням) — лента и карточка остаются дешёвыми. Обратная сторона —
денормализация: резерв меняется в тех же транзакциях, что и статусы.

**Защита от перепродажи — атомарный условный UPDATE, а не «прочитал →
проверил → записал»** (между чтением и записью конкурентная бронь успевает
влезть):

```sql
UPDATE listings
SET "quantityReserved" = "quantityReserved" + N
WHERE id = $1 AND "quantityAvailable" - "quantityReserved" >= N
```

0 затронутых строк → ConflictException. Уход в минус невозможен на уровне БД.
Возврат резерва (отмена/TTL) — симметричное условие `>= N`.

**Резерв перестраивается при принятии корректировки** (запрошено 20,
предложено 15 → резерв 20 → 15). До решения покупателя резерв держит
запрошенное количество — консервативно, зато остатки никогда не «плывут»
посреди переговоров.

### 4. TTL 30 минут

- Рынок работает 4:00–14:00, пик — до 9:00. Запрос, на который не ответили
  за полчаса, в этом темпе мёртв: покупатель уже купил у соседа по линии.
- 30 минут достаточно, чтобы продавец увидел заявку между покупателями
  (обычно отвечает за 5–10 минут).
- Значение осознанно настраивается через `BOOKING_TTL_MINUTES` (ENV):
  под утренний пик можно уменьшить без релиза.
- **Корректировка продлевает TTL заново**: переговоры не должны умирать
  по таймеру посреди разговора.
- Гашение — cron каждую минуту (`@nestjs/schedule`), для каждой брони —
  своя транзакция с перепроверкой статуса (кто-то мог успеть ответить
  между выборкой и гашением). Действия пользователя над истёкшей бронью
  отклоняются 409 ещё до крона — «зомби-брони» не живут.

### 5. Заглушка аутентификации X-User-Id

⚠️ Временное решение v0.2.0: клиент передаёт `X-User-Id`, guard загружает
пользователя из БД и прикрепляет к запросу. **Роль берётся из БД** —
подделать её заголовком нельзя; но перехватить чужой id — можно, поэтому
это допустимо только до настоящего входа (телефон + JWT, v0.3+). Guard
прикреплён явно к listings/bookings, `/health` остаётся анонимным.

### 6. Наблюдаемость

Каждый переход статуса — structured log (pino):
`bookingId`, `actorId`, `fromStatus`, `toStatus` — трассируется вся жизнь
брони. Плюс `BookingEvent` — тот же факт, но навсегда и с payload.

## Рассмотренные альтернативы

- **Продажа с мгновенным списанием остатка** — не рынок: покупатель хочет
  именно придержать товар до приезда, а продавец — отказаться или
  скорректировать.
- **«Опциональные» резервы (soft-hold без счётчика)** — перепродажа
  почти гарантирована в утренний пик.
- **Агрегация резерва `SUM(booking.requestedQuantity)` на лету** — честно,
  но лента из сотен лотов считает сотню агрегатов; для v0.2.0 несоразмерно.
- **PostgreSQL advisory locks / SERIALIZABLE** — избыточно: условный UPDATE
  решает задачу проще и быстрее.
- **Статус `pending_payment` и оплата в модели** — вне рамок v0.2.0
  (брони без денег), заложено в `confirmedQuantity` и журнал.

## Последствия

- ✅ Перепродажа исключена на уровне БД (e2e: резерв не уходит в минус).
- ✅ Полный аудит жизни брони: pino-логи + append-only журнал.
- ✅ Лента/витрина читают остаток без агрегаций.
- ⚠️ Денормализация: `quantityReserved` меняется только через сервис броней —
  прямые `prisma.listing.update` с полем резерва запрещены договорённостью
  (в v0.3 можно добавить DB-триггер).
- ⚠️ `X-User-Id` — не аутентификация; заменить на JWT до какого-либо
  прод-использования.
