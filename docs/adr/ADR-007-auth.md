# ADR-007: Аутентификация — телефон + SMS-код → JWT

- Статус: **Принято**
- Дата: 2026-11-05
- Этап: v0.3.0 «Аутентификация и офлайн-ядро»

## Контекст

v0.2.0 работала с заглушкой `X-User-Id`: клиент сам называл id
пользователя, API верил заголовку. Для «брони за 30 минут» этого
хватало, но любой человек с curl мог представиться кем угодно.
Пользователи рынка — продавцы, ларёчники, водители: у всех есть
телефон, и телефон уже служит идентификатором в мессенджерах и
списках контактов рынка. Пароли на этом фоне — лишний барьер:
забытый пароль в 5 утра на рынке не восстановить.

Нужна была полноценная аутентификация: телефон + код подтверждения,
токены, лимиты на запросы, смена роли на сервере.

## Решение

### 1. Вход: телефон + SMS-код

```
POST /auth/request-code { phone }   → код в Redis, TTL 5 минут
POST /auth/verify { phone, code }   → { accessToken, refreshToken, user }
POST /auth/refresh { refreshToken } → { accessToken }
```

- Телефон нормализуется к E.164 (+7XXXXXXXXXX) на клиенте и сервере
  одной функцией из `@agromoll/types` — «8 961 123 45 67» и
  «+7 (961) 123-45-67» дают один аккаунт.
- Пользователь создаётся при первом `request-code` с именем-заглушкой
  «Участник +7\*\*\*1234» и ролью buyer; `verify` ставит `phoneVerified`.
- **Код-заглушка в dev:** при `NODE_ENV=development` код фиксированный
  «0000» и печатается в лог. Подсказка «Код: 0000» видна на экране
  входа только в `__DEV__`. Почему: интеграция с SMS-провайдером
  (СМС-Центр, Twilio и т.п.) требует бюджета и номера отправителя —
  на этапе MVP это блокер, а не защита. При подключении провайдера
  меняется одна функция `requestCode`.
- `passwordHash` — nullable-колонка про запас (запасной вход для
  «телефон потерян»); в MVP не используется и не отдаётся наружу.

### 2. JWT: access 15 минут, refresh 30 дней

- **Access** (15 минут) живёт в каждом запросе `Authorization: Bearer …`.
  Короткий срок сужает окно утечки: токен в логах, скриншоте,
  mitm-прокси живёт минуты.
- **Refresh** (30 дней) хранится только в secure store (iOS Keychain /
  Android EncryptedSharedPreferences) и показывается серверу один раз —
  в `/auth/refresh`.
- Секреты `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` — из ENV, в
  production отсутствие секретов **роняет старт приложения**, а не
  первый запрос: ошибка конфигурации должна находить деплой, а не
  пользователя. Dev-дефолты — только для локальной разработки.
- Payload обоих токенов одинаков (`sub`, `role`), но подписи разными
  секретами: access-токен нельзя подсунуть вместо refresh.

### 3. JwtAuthGuard: роль из БД, а не из токена

Guard проверяет подпись и срок, затем **перечитывает пользователя из
БД** и прикрепляет к `request.user`. Дороже (запрос к БД на каждый
запрос), но:

- смена роли (`PATCH /users/me/role`) действует сразу, без перевыпуска
  токенов;
- удалённый/заблокированный пользователь не проходит даже с живым
  токеном;
- роль нельзя подделать, в отличие от v0.2.0.

`RolesGuard` и `@CurrentUser()` сохранены — проверка ролей теперь идёт
по свежим данным из БД. `X-User-Id` удалён полностью.

### 4. Почему refresh без revocation-списка (и чем это грозит)

Refresh-токен — plain JWT без серверного списка отзыва: выйти «со всех
устройств» нельзя, отзыв только временем (30 дней) или сменой секрета.
Для MVP это осознанный компромисс: список отзыва = Redis + таблица
сессий + UI управления устройствами — заметный объём работы при
минимальной выгоде на текущем этапе (устройство одно, пользователь
один). Задокументировано как долг v0.4+.

### 5. Rate limiting: 1 запрос в минуту НА ТЕЛЕФОН

`@nestjs/throttler` с кастомным трекером: базовый guard считает по IP,
а на рынке все за одним Wi-Fi — лимит по IP душил бы соседей.
Трекер берёт нормализованный `phone` из тела, fallback — IP.
429 при повторе. Защита от SMS-флуда (деньги за каждую отправку)
и от перебора кодов.

### 6. Одноразовость кода и защита от перебора

- Код живёт 5 минут (TTL Redis `EX`), удаляется после успешной
  проверки — повторно воспользоваться нельзя;
- неверный код НЕ сжигает попытку (можно перепечатать опечатку),
  но сам код угадывается за минутные окна rate limit-ом request-code;
- e2e-тесты читают код из того же хранилища, что и приложение
  (`app.get(CODE_STORE)`), — тестируется реальный путь без дыр
  в проде.

### 7. Хранилище кодов: Redis с in-memory fallback

Redis выбран ради TTL из коробки и общей памяти между репликами API
(код должен работать при нескольких инстансах). Если `REDIS_URL`
не задан — in-memory Map с предупреждением в лог: режим для локальной
разработки и e2e, в production обязателен Redis (CI поднимает
service-контейнер).

### 8. Клиент: axios-интерцептор с single-flight refresh

- 401 от API → **один общий** refresh (single-flight: параллельные
  запросы ждут один промис, а не устраивают гонку) → повтор исходного
  запроса с новым токеном;
- refresh не удался → токены стираются, событие `agromoll:auth-sign-out`
  → auth-store переводит приложение на экран входа;
- при старте: есть refresh-токен → пробуем refresh + `GET /users/me`
  (профиль с ролью), нет → экран входа.

### 9. Роль — на сервере

Выбор роли на экране входа и «Сменить роль» идут через
`PATCH /users/me/role`; локальный role-store v0.2.0 удалён.
Роль видна с любого устройства и сразу действует в RolesGuard.

### 10. Безопасность на MVP: что принято и что нет

Принято: JWT с коротким access, secrets из ENV, маскировка телефона
в логах (`+7***1234`, без кодов и токенов), rate limit, одноразовые
коды, secure storage, разные секреты access/refresh.

Не принято (долги v0.4+): SMS-провайдер (код-заглушка в dev),
revocation-список refresh, 2FA для продавцов с большими оборотами,
PIN-код на входе в приложение (биометрия expo-local-authentication).

## Последствия

- `X-User-Id` исчез из кодовой базы: все эндпоинты listings/bookings/
  users требуют живой access-токен (401 без него — покрыто e2e);
- любой новый эндпоинт получает защиту декораторами `@UseGuards(JwtAuthGuard, RolesGuard)`
  и `@Roles(...)` — конвенция v0.3+;
- e2e-тесты регистрируют пользователей через реальный флоу
  (request-code → verify → PATCH role), поэтому покрывают и auth;
- seed v0.3.0 создаёт демо-аккаунты с телефонами — вход в dev
  по коду «0000» работает и на сид-данных.
