# ADR-006: Офлайн-ядро — outbox, идемпотентность, конфликты

- Статус: **Принято**
- Дата: 2026-11-05
- Этап: v0.3.0 «Аутентификация и офлайн-ядро»

## Контекст

Рынок работает рано утром, мобильный интернет на площадке нестабилен:
сеть пропадает на минуты, запросы теряются на нестабильном соединении.
Пользователь при этом не должен «терять» действия: бронь, созданная
в лифте/подвале/толпе, обязана дойти до продавца, когда сеть вернётся.
Обратная сторона той же проблемы — повторы: клиент, не получивший ответ,
шлёт запрос снова, и без защиты на сервере рождается дубль брони,
который «съедает» остатки других покупателей.

Нужен фундамент (без бизнес-фич поверх): локальная очередь мутаций на
клиенте, идемпотентность на сервере и честное разрешение конфликтов.
Долги (289-ФЗ) и приёмка доставки построятся на этом же каркасе в v0.4+.

## Решение

### 1. Общая схема

```
UI (оптимистично) ──► локальный outbox (SQLite) ──► сеть ──► API
                        X-Idempotency-Key: clientUuid
                                                    │
                              OutboxOperation (Postgres, unique clientUuid)
                                                    │
                                              handler → result
```

Каждая мутация получает UUID (uuid v4, `expo-crypto`) — **clientUuid**.
Клиент хранит операцию локально и шлёт её с заголовком
`X-Idempotency-Key`. Сервер резервирует ключ уникальным индексом,
выполняет операцию один раз и сохраняет результат: повторный запрос
с тем же ключом получает сохранённый ответ, не выполняясь снова.
Это стандартный паттерн transactional outbox / идемпотентного ключа
(его используют Stripe `Idempotency-Key` и HTTP-семантика 409/425).

### 2. Локальное хранилище: expo-sqlite, а не WatermelonDB

Выбран **expo-sqlite**:

- нам нужна простая FIFO-очередь из одной таблицы без реактивных связей
  и без синхронизации серверных данных — WatermelonDB решает задачу
  «офлайн-кэп сложных моделей», которой у нас ещё нет (данные читаются
  напрямую из API, кэшировать их в БД на MVP не требуется);
- ~200 строк кода против тяжёлой ORM-зависимости с собственным
  генератором схем и миграциями;
- WAL-режим и один поток записи — очередь маленькая (десятки операций),
  конкуренции нет;
- у WatermelonDB есть преимущества (реактивные подписки, связи),
  которые станут полезны, если в v0.4+ решим кэшировать ленту —
  переезд не блокирует: интерфейс `OutboxStorage` абстрагирует хранилище.

Схема живёт в самом модуле (`CREATE TABLE IF NOT EXISTS`): у очереди
одна версия на MVP, отдельного механизма миграций не заводим.

### 3. Шесть состояний операции

```
pending ──► processing ──► completed
   │            │
   │            ├──(сеть/5xx/409-в-обработке)──► retrying ──(backoff)──► processing…
   │            ├──(бизнес-409)───────────────► conflicted ──(человек)──► удаление
   │            └──(прочие 4xx)───────────────► permanently_failed
   └──(возврат в очередь) retryManually
```

- **pending** — в очереди, не отправлялась;
- **processing** — отправляется прямо сейчас (видно на экране «Очередь»);
- **retrying** — сеть/сервер недоступны, ждём с экспоненциальным backoff
  **1с → 2с → 4с → 8с → 16с, максимум 5 попыток**;
- **conflicted** — сервер отверг по бизнес-правилу (бронь уже отменена,
  лот снят). Молча решать нельзя — диалог с человеком;
- **permanently_failed** — безнадёжно (4xx: валидация, права). Повтор
  вручную возможен с экрана «Очередь»;
- **completed** — сервер подтвердил, оптимистичное состояние снято.

Почему failed-состояний два: повтор имеет смысл только там, где причиной
была инфраструктура (сеть, 5xx). Повторять запрос с битым телом или
нарушенной бизнес-логикой бессмысленно — он упадёт так же.

### 4. Серверная сторона: OutboxOperation + @Idempotent

Таблица `outbox_operations`: `clientUuid` (уникален глобально),
`userId`, `operationType`, `payload`, `result` (`{status, body}`),
`state` (`received`/`processed`/`failed`). Строки не удаляются —
это журнал того, какие операции клиент уже провёл.

`IdempotencyInterceptor` (глобальный, активируется декоратором
`@Idempotent('create_booking')`):

- нет заголовка → обычное выполнение (обратная совместимость —
  curl-эксперименты и старые клиенты не ломаются);
- новый ключ → вставка `received` (уникальный индекс = защита от
  параллельных дублей) → выполнение → `processed` + результат;
- `processed` → реплей сохранённых статуса и тела без выполнения;
- `received` (параллельный дубль) → **409** `{code: IDEMPOTENCY_IN_PROGRESS}`;
- `failed` → повторное выполнение в той же строке (клиент после backoff
  имеет право на ещё одну попытку с тем же ключом);
- чужой `userId` → 409 без деталей (не раскрываем чужие операции).

Помечены все пять мутаций броней: `POST /bookings`, `/:id/cancel`,
`/:id/confirm`, `/:id/counter-offer`, `/:id/accept-counter`.

**Отступление от ТЗ (зафиксировано в отчёте):** в спецификации enum
`operationType` содержал только `create_booking`, `cancel_booking`,
`confirm_booking`, `create_debt`, `confirm_delivery`, но при этом
требовал идемпотентности на 5 эндпоинтах, включая counter-offer
и accept-counter. Enum расширен значениями `counter_offer_booking`
и `accept_counter_booking` — иначе два эндпоинта осталось бы
не защищёнными.

### 5. Конфликты: человек, не автоматика

409 бывает двух видов, и клиент их различает:

- **409 IDEMPOTENCY_IN_PROGRESS** — операция уже в обработке сервером:
  короткий retry через 2 секунды, пользователю невидима;
- **бизнес-409** («бронь уже отменена») — операция уходит в
  `conflicted`, UI показывает диалог:
  **«Бронь уже была отменена на сервере. Что делаем?
  [Принять серверное] [Отменить локальную]»**.
  Оба варианта удаляют локальную операцию; «Принять серверное»
  дополнительно перечитывает данные с сервера.

Почему не автоматически: «выиграть» конфликт за пользователя значит
тихо стереть либо его действие, либо действие контрагента. На рынке
это деньги и товар — решение остаётся за человеком.

### 6. Триггеры синхронизации

Очередь догоняется: при старте приложения, при восстановлении сети
(NetInfo), при возвращении на передний план (AppState), при
pull-to-refresh и вручную (кнопка на экране «Очередь»).

### 7. Почему НЕ background sync на iOS (пока)

iOS даёт ~30 секунд фонового исполнения после сворачивания и не
гарантирует его для arbitrary-задач (только BGAppRefreshTask по
расписанию системы с задержками в минуты/часы). Для рынка это
бесполезно: окно жизни брони — 30 минут, синхронизация нужна в момент
разблокировки экрана, а AppState `active` это покрывает. Background
fetch добавим, если появятся сценарии доставки «положил телефон
в карман и поехал» (v0.4+, попутные доставки).

### 8. Разграничение сессий

Выход из аккаунта очищает локальную очередь и оптимистичные состояния:
операции одного пользователя не должны уехать от имени другого
(телефон могут передать напарнику). `signOut` в auth-store делает
это атомарно вместе с удалением токенов.

### 9. Индикатор в шапке

Маленькая точка и текст: зелёная «Онлайн», янтарная «Офлайн — сохраним»,
пульсирующая зелёная «Синхронизация…» (очередь не пуста и есть сеть).
Без красного (ADR-002). Тап открывает экран «Очередь» — прозрачность:
пользователь всегда видит, что его действия ещё не дошли.

## Последствия

- «Ровно один раз» между клиентом и сервером гарантируется парой
  (локальный clientUuid + уникальный индекс) — дублей брони больше
  не бывает даже при обрывах в самый неподходящий момент;
- все новые мутации (долги, приёмка) обязаны проходить через outbox
  и получать `@Idempotent` на сервере — это стандарт разработки v0.4+;
- строки `outbox_operations` растут бесконечно — чистка по возрасту
  запланирована в v0.4 (пока объёмы пренебрежимы: десятки строк
  на пользователя в день);
- оптимистичный UI охватывает брони; витрина (создание лотов) остаётся
  онлайн-операцией — продавец выставляет лот со стабильной точки,
  покупатель бронирует «в поле».
