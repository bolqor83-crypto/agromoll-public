# ADR-013: Публичный рейтинг — ReputationSnapshot, веса, анти-накрутка

- Статус: **Принято**
- Дата: 2026-11-08
- Этап: v0.5.0 «Публичный рейтинг · Геозоны · Доставка попутчиками» (подэтап A)

## Контекст

Рынок живёт доверием: покупатель выбирает продавца по картинке и цене,
не зная, срывал ли тот поставки; продавец отпускает в долг, не зная,
возвращал ли покупатель деньги. С v0.4.0 у нас накопился источник
правды: append-only журналы `BookingEvent` (приёмка ok/minor/disputed,
авто-подтверждение) и `DebtEvent` (погашения и споры). Пора превратить
их в публичную, простую и объяснимую метрику.

Требования v0.5.0-A: рейтинг 0–5, расчёт из BookingEvent + DebtEvent,
API `/reputation/:userId` (публичный) и `/reputation/me` (свой, с
историей), анти-накрутка против «дружеских» сделок, пересчёт не должен
ломать сделку.

## Решение

### Формула: 0–5, одна цифра, объяснимая

```
score = 5 × (Σpositive − Σnegative) / N,   кламп в [0, 5]
```

- `N` — число учтённых событий (сделки, авто-подтверждения, споры,
  погашения/споры по долгам).
- Каждое событие несёт положительный вклад `positive` (0…1) и/или
  отрицательный `negative` (0…1).

Почему шкала 0–5: рынок привык к «звёздам» (Яндекс Карты, Wildberries,
Отзовик) — «4.7» считывается мгновенно, «0.94» — нет. Пять — потолок
безопасности: шкала 0–10 поощряет сравнивать десятые доли там, где
данных на это нет.

Почему нормализация именно (pos − neg)/N: это доля «идеальности»
участника. 4 идеальных сделки + 1 спор → (4 − 1)/5 = 0.6 → 3.0 —
интуитивно «хорошо, но с пятном». Формула линейна, устойчива к
объёму и объясняется одной фразой на экране.

### Веса (ENV, дефолты — спецификация v0.5.0-A)

| Событие | positive | negative | Кому |
| --- | --- | --- | --- |
| `delivery_confirmed` (ok) | 1.0 | — | продавцу и покупателю |
| `delivery_confirmed` (minor_issue) | 0.5 | — | продавцу; покупателю 1.0 |
| `system_auto_confirmed` | 0.3 | — | обеим сторонам |
| `delivery_disputed` | — | 1.0 | только продавцу |
| долг `settled` (без спора) | 1.0 | — | дебитору |
| долг `disputed` (не разрешён) | — | 1.0 | дебитору |
| спор долга разрешён обоюдно (`resolve_confirmed`) | 0 | 0 | нейтрален, исключается |

Почему auto-confirm весит 0.3, а не 1.0: авто-подтверждение — это
«покупатель не пришёл и не нажал кнопку». Сделка состоялась, но
участник в ней пассивен. Полный вес разрушил бы смысл явного
подтверждения: рейтинг рос бы сам, по таймеру.

Почему minor_issue даёт покупателю полный вес: qualityFlag — претензия
к качеству товара, а качество — зона ответственности продавца.
Покупатель свою часть сделки выполнил: забрал, принял, подтвердил.

Почему спор по качеству нейтрален покупателю: покупатель, заявивший
major_issue, уже «потратил» сделку на спор. Минусовать его за
активную защиту своих интересов — наказывать честность.

Почему спор долга разрешённый — нейтрален: обоюдное разрешение
означает «стороны договорились» — часто это недоразумение, а не
обман. Нейтральность разрешённых споров оставляет путь к
восстановлению рейтинга через договорённость. Технически: события
`disputed` и `resolve_confirmed` одного долга взаимно исключаются из
расчёта.

### Порог RATING_MIN_DEALS (по умолчанию 5)

Если учтённых событий меньше порога — `score = null`, API возвращает
`{ score: null, reason: "min_deals_not_reached" }`.

Почему null, а не «0.0»: новичок с двумя сделками и цифрой «2.8» на
карточке проигрывает ветерану с «4.6» не по делу — у него просто
мало данных. Null = «рейтинга ещё нет», бейдж не рендерится. Это
снимает порог входа: первые сделки не должны наказывать.

`/reputation/me` дополнительно возвращает `dealsToRating` — сколько
взвешенных событий не хватает, экран показывает «Сделайте ещё N
сделок, чтобы получить рейтинг».

### Анти-накрутка: пары и окно

Если пара «покупатель — продавец» совершила больше
`RATING_MAX_PAIR_DEALS` (10) сделок за `RATING_PAIR_WINDOW_DAYS` (30)
дней, ВСЕ сделки этой пары в окне считаются с весом
`RATING_PAIR_CAP_WEIGHT` (0.3).

Как это защищает: «дружеская» накрутка — это всегда узкая пара
участников, гоняющая брони друг по другу. Честный оптовый рынок —
много разных контрагентов (продавец торгует с десятками покупателями).
После капа 12 сделок одной пары дают score 1.5 вместо 5.0: накрутка
не окупается. Порог 10 выбран с запасом: реальная пара
«постоянный клиент — продавец» делает 4–8 сделок в месяц, и только
аномальная активность попадает под кап.

Окно 30 дней, а не «за всё время»: рынок сезонный, постоянные
контрагенты накапливают десятки сделок за год — это честная история.
Капли только свежая аномальная концентрация.

### Модель данных

- `ReputationSnapshot` — один снимок на пользователя (уникальный
  `userId`): `score` (nullable!), счётчики, `lastCalculatedAt`.
  Материализованное представление для дешёвых публичных чтений
  (бейджи на карточках — joins в запросах листингов/броней/долгов).
- `ReputationEvent` — append-only журнал (аудит): что случилось с
  рейтингом (`deal_confirmed`, `dispute_opened`, `dispute_resolved`,
  `auto_confirmed`, `penalty_applied`), delta и reason. Питает
  таймлайн экрана «Мой рейтинг». Индекс `userId+createdAt`.

Источник правды — ЖУРНАЛЫ BookingEvent/DebtEvent, не снимок:
пересчёт идемпотентен и пересчитывает историю целиком.

### Триггеры и неблокирующий пересчёт

Пересчёт запускают: `confirm-delivery` (completed/disputed),
авто-подтверждение по крону, `settle`/`dispute`/`resolve` долга.

Триггер вызывается ПОСЛЕ фиксации бизнес-транзакции, в собственной
транзакции пересчёта, обёрнут в try/catch (`safeOnBookingDelivery` /
`safeOnDebtChanged`): упавший пересчёт логируется, но НЕ откатывает
сделку. Обоснование: рейтинг — производная величина; цена потери
«сделка не завершилась из-за рейтинга» несоизмерима с ценой
«рейтинг пересчитается на следующем событии». Самопочинка: каждый
триггер пересчитывает всё с нуля, поэтому пропущенный пересчёт
догоняется любым следующим событием.

### API

- `GET /reputation/:userId` — публичный профиль (score, счётчики,
  lastCalculatedAt). Если снимка нет — расчёт на лету без записи
  (чтения не пишут). 404 для неизвестного пользователя.
- `GET /reputation/me` — свежий расчёт + `dealsToRating` + последние
  20 событий журнала.
- Оба — за JWT (рынок для своих), но рейтинг любого участника виден
  любому аутентифицированному — в этом «публичность».

Листинги, брони и долги несут рейтинги сторон прямо в DTO
(`sellerRating`, `buyerRating`, `creditorRating`, `debtorRating`) —
бейдж на карточке не требует N+1 запросов.

### Мобильный клиент

- `RatingBadge` «4.7 · 42 сделки»: зелёный ≥ 4.0, янтарный ниже,
  null не рендерится.
- Бейджи: карточка листинга (рейтинг продавца), карточки броней
  (рейтинг контрагента), карточки долгов (рейтинг контрагента).
- Экран «Мой рейтинг»: score/подсказка прогресса, счётчики, таймлайн
  событий. Вход — карточка на экране выбора роли.

## Последствия

- Счётчики `User.totalConfirmations`/`totalDisputes` (v0.4.0-C)
  остаются быстрыми счётчиками приёмок; рейтинг считает сервис
  репутации по журналам — источники не конфликтуют.
- Изменение весов через ENV меняет рейтинг только при следующем
  триггере (пересчёт ленивый) — для мгновенного пересчёта всех
  нужна фоновая задача (не в v0.5.0).
- Арбитраж споров (изменение итога disputed-брони) — v0.6.0;
  пока спор по качеству необратим и весит −1.0 для продавца.
