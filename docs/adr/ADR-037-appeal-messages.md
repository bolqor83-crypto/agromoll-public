# ADR-037: Переписка в апелляциях на блокировки 289-ФЗ

- Статус: принято (v0.7.0-C)
- Дата: 2026-11-07
- Связанные: ADR-035 (апелляции), ADR-033 (арбитраж споров — источник
  паттерна), ADR-031 (push-уведомления)

## Контекст

Апелляция с v0.6.0-E — это «reason + решение»: жалоба стороны пары и
вердикт арбитра. Если арбитру нужно уточнить обстоятельства (какие смены
задвоились? есть ли накладные?) — он не мог спросить: приходилось решать
по истории часов вслепую или отклонять «за недостатком данных». Сторона
пары, в свою очередь, не могла дополнить жалобу после подачи.

В спорах (ADR-033) переписка уже есть и показала себя: кейсы решаются
быстрее, когда арбитр задаёт вопросы прямо в кейсе.

## Решение

**AppealMessage — зеркально DisputeMessage.**

- Модель: `id, appealId (FK, cascade), authorId, body, isInternal,
  createdAt` + индекс `(appealId, createdAt)`.
- **Append-only**: правки и удаления запрещены и API, и моделью —
  переписка кейса это журнал разбирательства; «отредактированное»
  доказательство в арбитраже хуже отсутствия доказательства.
- **isInternal — служебные заметки арбитра**: арбитр фиксирует ход
  проверки («сверил журнал смен — дубли подтверждены»), не показывая
  паре промежуточные выводы. Стороне пары — 403 при попытке создать,
  заметки фильтруются из деталей и списка (паре не виден сам факт их
  существования).
- Доступ: сторона пары (driver/seller) или арбитр; посторонним — 404
  (не раскрываем факт существования кейса — как в ADR-035).
- Переписка доступна только в АКТИВНОМ кейсе (open/under_review);
  после решения — 409 на новые сообщения, история читается в деталях
  (журнал сохраняется для аудита).

### Эндпоинты

- `POST /appeals/:id/messages` `{body, isInternal?}` — идемпотентно
  (`appeal_message` в OutboxOperationType);
- `GET /appeals/:id/messages` — список с той же фильтрацией по роли;
- `GET /appeals/:id` (детали) теперь включает `messages` — экран
  получает всё одним запросом, отдельный эндпоинт остаётся для
  обновления списка без перезагрузки кейса.

### Уведомления

Новое публичное сообщение → push (type `appeal_message`) обеим сторонам
пары и назначенному арбитру, кроме автора — тот же адресатный принцип,
что в спорах (`notifyCaseActivity`, ADR-033). Служебные заметки никого
не уведомляют: пара о них не знает.

### Мобильные экраны

- **Пара**: новый маршрут `/appeal/[id]` (AppealDetailScreen) — таймлайн,
  поле ответа, история месяцев часов (доказательство). Вход — из карточки
  пары на экране часов: бейдж «Апелляция: … · переписка» и подпись стали
  нажимаемыми. До v0.7.0-C пара ждала решения «вслепую».
- **Арбитр**: в ArbitrationScreen секция деталей апелляции получила
  таймлайн + ввод с переключателем «Паре / Служебная» (как в кейсах
  споров).
- Push `appeal_message` маршрутизируется по роли: паре — на экран часов
  (там вход в кейс), арбитру — в арбитраж.

## Альтернативы

- **Переиспользовать DisputeMessage с полем caseType** — слил бы две
  сущности с разным предметом (спор о сделке vs обжалование блокировки
  пары): разные стороны, разный предмет заморозки, разная судьба.
  Дублирование простой append-only таблицы дешевле связности.
- **Чат в реальном времени (WebSocket)** — переписка апелляции это
  десяток сообщений за жизнь кейса; polling при открытии экрана и push
  о новом сообщении решают задачу без постоянных соединений.

## Тестирование

- Unit: доступ (посторонний — 404), isInternal только арбитру (паре 403),
  закрытый кейс — 409, фильтрация видимости в listMessages/findOne,
  адресаты уведомлений (вторая сторона + арбитр, не автор).
- E2E: арбитр спрашивает публично → пишет служебную → сторона отвечает
  (403 на её служебную) → видимость в деталях (водитель 2, арбитр 3) →
  посторонний 404 → push второй стороне → решение закрывает переписку
  (409), история читается.

## Последствия

- Миграция: таблица `appeal_messages` + `appeal_message` в enum'ах
  OutboxOperationType и NotificationType;
- API: два новых эндпоинта, детали апелляции расширены (обратно
  совместимо — аддитивное поле);
- мобильное: новый экран + маршрут `/appeal/[id]`, нажимаемый бейдж
  в «Моих часах», маршрут push-уведомлений.
