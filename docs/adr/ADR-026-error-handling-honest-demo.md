# ADR-026: Обработка ошибок и честный демо-фолбэк

- Статус: **Принято**
- Дата: 2026-11-06
- Этап: v0.6.1 «Mobile UX Excellence» (подэтап D)

## Контекст

Инвентаризация v0.6.1 выявила три класса нечестности в состояниях экранов:

1. **Молчаливые ошибки.** Радар и доставка при ошибке первой загрузки
   оставляли `deliveries === null` — экран вечно показывал skeleton,
   ошибка уходила только в console.warn. Пользователь смотрел на
   «загрузку», которой уже не будет.
2. **Фальшивые данные как «успех».** «Мои брони», «Входящие», лента и
   витрина при недоступном API подставляли демо-объекты с маленьким
   бейджем «Демо-данные» в шапке. Покупатель мог решить, что брони
   настоящие; продавец — «подтвердить» несуществующую бронь (кнопки
   перехватывались Alert-ом, но картинка была обманчива).
3. **Разнобой формулировок.** Каждый экран придумывал свой текст ошибки
   («Радар недоступен», «Доставка недоступна», «Не удалось загрузить») и
   свою комбинацию EmptyState/Alert.

Плюс диагностическая дыра: NetInfo-слушатель в outbox-бридже не логировал
состояния сети — флаги «офлайн»/«синхронизация» в ConnectionBadge нечем
было разбирать в headless-средах.

## Решение

### Вариант A — без фейков: радар, «Мои брони», «Входящие», доставка (обе)

Конечный автомат `loading → ready | error` на каждый экран:

- **loading** → skeleton (как раньше);
- **error (первая загрузка)** → полноэкранный `ErrorState` с заголовком,
  пояснением и кнопкой «Повторить»;
- **ready + staleError (рефреш не удался, данные уже на экране)** →
  данные остаются, сверху inline-ErrorState «Данные могли устареть»:
  не прячем то, что пользователь уже видел, но и не притворяемся, что
  всё свежо.

Почему без демо-данных именно здесь: радар, брони и доставки — это
**деньги и обязательства** (взял заказ, должен отвезти; подтвердил бронь —
резерв). Выдуманные «попутные заказы» или «успешные брони» при мёртвом
API создают ложные ожидания. Исключение — локальные офлайн-брони из
outbox: они **настоящие** (созданы пользователем, ждут сети), поэтому
при ошибке показываются вместе с inline-ошибкой, а не прячутся.

### Вариант B — демо с честным баннером: лента, витрина

Лента и витрина — «витрина продукта»: показать, как выглядит рынок,
можно и без сервера. Демо-данные остаются, но:

- полноширинный янтарный `DemoBanner` под шапкой: «Демо-режим. API
  недоступен. Данные не настоящие» (+ подсказка, какие кнопки отключены);
- кнопки, которым нужен сервер, отключены: на ленте — «Рядом со мной» и
  «Моя точка», на витрине — FAB «Выставить лот» (приглушён до 40%,
  `accessibilityState.disabled`) и «Моя линия на карте». Маленький
  бейдж в шапке удалён — его заменяет баннер, который не пропустишь.

**INVALID_RESPONSE — не демо, а ошибка.** Если сервер ответил, но формат
не прошёл zod-валидацию (ADR-006), это баг сериализации, а не «нет
сервера»: показываем ErrorState, никаких витрин.

### ErrorState унифицирован в packages/ui

Один компонент для всех экранов (`packages/ui/src/components/ErrorState.tsx`):

- `variant="full"` — иллюстрация «нет связи» (облако с чертой, янтарный
  круг, scale 0.9→1 spring — как EmptyState, ADR-009), заголовок,
  пояснение, «Повторить»;
- `variant="inline"` — компактный янтарный блок без иллюстрации (для
  stale-данных и локальных офлайн-броней);
- `accessibilityRole="alert"` + testID — ошибка видна скринридеру
  и тестам.

ErrorState отдельный от EmptyState, потому что **пустое ≠ сломанное**:
«Новых броней нет» и «Нет связи с сервером» — разные сообщения с разными
действиями (первое — подождать, второе — повторить).

### Единый маппинг текстов

`apps/mobile/src/lib/error-content.ts`: код `ApiError` → { title,
description }. Экраны не придумывают формулировки. Тексты без
жаргона («ECONNREFUSED», «500»), без вины пользователя; для NETWORK
объясняют, что офлайн-действия сохранятся (у нас outbox, ADR-006).

### NetInfo-логирование

Слушатель в `initOutboxBridge` теперь пишет structured-лог на каждое
событие: `type`, `isConnected`, `isInternetReachable`, вычисленное
`isOnline` и прежнее `wasOnline`. Переходы offline → видны в логах,
загадочные «ConnectionBadge не отреагировал» — расследуемы.

## Почему демо-фолбэк — временная мера, а не архитектура

Демо-режим решает одну задачу MVP: показать продукт инвестору/партнёру
без деплоя API. Это НЕ фича для пользователей: с настоящим сервером
(см. хотфикс v0.6.1-0 и docs/DEPLOY.md) демо-ветки недостижимы. Как
только появится стабильный demo-стенд API, демо-данные из кода следует
убрать (лента/витрина/детали лота/долги) — «витрина продукта» будет
жить на сервере, а не вшитой в bundle. Долговременная архитектура —
вариант A везде.

## Тестирование

- `error-content.test.ts` — маппинг всех кодов + полный путь
  AxiosError → toApiError → текст (настоящем api-модуле);
- `RadarScreen.test.tsx` — три сценария (INVALID_RESPONSE, network, 500)
  → ErrorState с «Повторить», не вечный skeleton; retry перечитывает;
- `BookingsScreen.test.tsx` — ошибка без фейков; локальная офлайн-бронь
  видна вместе с ошибкой;
- `InboxScreen.test.tsx`, `DeliveryScreen.test.tsx` — вариант A;
- `FeedScreen.test.tsx`, `ShowcaseScreen.test.tsx` — вариант B: DemoBanner
  - отключённые кнопки; INVALID_RESPONSE → ErrorState без демо;
- `DemoBanner.test.tsx` — тексты, testID, alert-роль.

Моки: `@/test/screen-mocks.ts` (api, сторы, router), глобально в
jest.setup — Ionicons (реальный требует expo-font) и safe-area
(официальный jest-mock библиотеки).

## Последствия

- Экран никогда не молчит: любая ошибка = видимое состояние + повтор.
- Удалены `DEMO_BUYER_BOOKINGS` / `DEMO_COUNTER_OFFERS`; компоненты
  BookingCard / IncomingBookingCard / CounterOfferModal очищены от
  демо-веток.
- DebtSummaryWidget и ListingDetailScreen сохраняют прежнее поведение
  (виджет скрывается при ошибке; детали лота — демо-фолбэк с бейджем,
  согласован с демо-лентой варианта B) — кандидат на унификацию
  при удалении демо-данных.
