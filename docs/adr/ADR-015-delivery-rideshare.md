# ADR-015: Доставка попутчиками — цена вне платформы, 289-ФЗ при взятии, TTL запросов

- Статус: **Принято**
- Дата: 2026-11-08
- Этап: v0.5.0 «Публичный рейтинг · Геозоны · Доставка попутчиками» (подэтап C)

## Контекст

У рынка есть физическая логистика: покупатель забирает товар с линии
продавца сам, но не у каждого есть машина. Попутная доставка —
«водитель всё равно едет мимо, пусть подвезёт». Спецификация v0.5.0-C
требует: запросы доставки, ленту «кто едет куда», интеграцию с
учётом часов 289-ФЗ (ADR-011) и QR-подтверждение передачи.

## Решение

### Модель

`DeliveryRequest`: покупатель (buyer) просит подвезти от точки забора
(`pickupPointId` → GeoPoint-линия продавца) до точки выгрузки
(`dropoffPointId` → GeoPoint-точка покупателя). Статусы:
`open → assigned → in_transit → delivered` (+ `cancelled`/`expired`).
`DeliveryEvent` — append-only журнал переходов + попытки блокировок.

**Продавец для пары 289-ФЗ = владелец точки забора**
(`pickupPoint.owner`). Доставка в терминах трудовых отношений —
работа водителя с продавцом, чей товар он везёт: пару определяет
забор, а не выгрузка.

### Цена: платформа НЕ агент

В `DeliveryRequest` поля цены нет — намеренно. Водитель и стороны
договариваются сами при контакте. Почему:

- российское законодательство о платёжных агентах (161-ФЗ) и
  фискальные обязательства превращают «платформу, которая называет
  цену доставки» в агента с кассой, чеками и ответственностью за
  споры;
- цена попутной доставки — переговорная величина (попутно/нет,
  вес, габариты, время суток) — фиксированная комиссия убила бы
  саму идею «по пути»;
- UI честно предупреждает: «цену называет водитель при контакте».

### 289-ФЗ: BlockedPair при взятии, WorkSession при взятии

Интеграция с ADR-011:

1. **Создание запроса НЕ проверяет блокировки**: покупатель
   свободно просит доставку у любой линии. Запрос открыт ВСЕМ
   водителям — блокировка пары (driver, seller) — отношение
   конкретной пары, а не заказа.
2. **При взятии (assign)**: пара (водитель, точка-забора-владелец)
   заблокирована → **409 `DELIVERY_PAIR_BLOCKED`** с мягким
   сообщением («попробуйте другого продавца или подождите»), запрос
   остаётся открытым другим водителям, попытка фиксируется в журнал
   (`blocked_by_289fz` — аудит для поддержки).
3. **WorkSession создаётся при взятии, а не при создании запроса**:
   часы 289-ФЗ считают фактическую работу пары. Покупательский
   запрос, который никто не взял, — это не работа. Взяли — водитель
   принял обязательство забрать товар у этого продавца: смена
   пары началась. Одна открытая смена на водителя (как в ADR-011):
   взял заказ с другой линией — сначала заверши текущий.
4. **При завершении (deliver) или отмене взятого**: смена пары
   закрывается (`durationMinutes`), часы уходят в
   `MonthlyPairTotal`, и СРАЗУ проверяется серия месяцев —
   при закрытой серии `BlockedPair` создаётся, не дожидаясь крона
   03:00 (`enforceSeriesForPair`). Блокировка настигает пару в
   моменте, а не на следующее утро.

### TTL: открытый запрос живёт 60 минут

`DELIVERY_TTL_MINUTES=60` (ENV), крон каждые 5 минут гасит
просроченные (`open → expired`). Почему TTL: рынок живёт утром;
«висящий» трёхдневный заказ порождает ложные ожидания и захламляет
радар. 60 минут — окно реальной утренней логистики. expired —
терминальный: историю видно, повтор — новый запрос (цены и
резервов нет, откатывать нечего).

### Отмена

- до выезда (`open`/`assigned`) — любая сторона, свободно;
- после выезда (`in_transit`) — только водитель, с обязательной
  причиной (товар уже в пути, покупатель должен знать почему);
- смена пары закрывается и при отмене взятого заказа — часы честные.

### QR-подтверждение передачи

При создании генерируются `pickupCode`/`dropoffCode` (UUID).
Водитель показывает QR контрагенту; покупатель сверяет код
(сканер камеры на native через expo-camera / ручной ввод на web).
Подтверждение — клиентская сверка совпадения, без серверного раунда:
это ритуал доверия, а не юридический факт (платформа не агент).
Коды видны ТОЛЬКО сторонам (покупателю и назначенному водителю) —
радар их не получает.

### Идемпотентность

Все пять мутаций — через `@Idempotent` (ADR-006): `create_delivery`,
`assign_delivery`, `start_delivery`, `deliver_delivery`,
`cancel_delivery`. Офлайн через outbox идёт только СОЗДАНИЕ: взятие и
шаги — прямые онлайн-вызовы, потому что сервер в момент взятия
проверяет BlockedPair и открытые смены — офлайн-очередь здесь
исказила бы смысл проверки.

### API

`POST /deliveries` (buyer) · `GET /deliveries/open` (driver, радар) ·
`GET /deliveries/me` · `POST /deliveries/:id/assign|start|deliver|cancel`.

Радар: если у водителя есть активные коридоры (ADR-014) — только
заказы, чьи точки забора/выгрузки в `DELIVERY_CORRIDOR_MATCH_METERS`
(2000 м) от линии маршрута, отсортированные по «попутности»
(расстояние точка→отрезок, сферический cross-track); без коридоров —
все открытые (водитель сам решает, а публикация маршрута — один тап
на «Карте рынка»).

### Mobile

- **Радар** (driver): карточки «откуда → куда», вес, янтарный
  TTL-таймер, попутность; «Беру» — крупная кнопка в нижней трети;
  409 289-ФЗ — мягкий экран-пауза.
- **Мои доставки** (driver): пошаговый сценарий «Заберите на линии →
  QR продавцу → Везите → QR покупателю», QR-коды передачи, действия
  по статусу; отмена после выезда — с inline-причиной.
- **Доставка** (buyer): список запросов + создание через
  `CreateDeliverySheet` (линии продавцов рядом, мои точки, вес);
  сверка QR водителя (сканер/ввод).

## Последствия

- Арбитраж споров доставки — v0.6.0 (журналы событий готовы).
- Уведомления о статусах доставки (push) — v0.6.0: сейчас покупатель
  видит статус на своём экране и в «Моих доставках» водителя.
- Ограничение «одна открытая смена» делает параллельный приём двух
  заказов невозможным — сознательно (289-ФЗ считает пару, «две
  линии одновременно» — это уже не попутная доставка).
